# Doclify model bridge foundation

This standalone Rust library invokes Claude Code in noninteractive print mode (`--output-format stream-json --verbose`) with built-in tools disabled, restricted and safe modes, strict MCP configuration, no persisted session, no slash commands and no interactive permission grants. It sends the prompt over stdin, verifies the runtime restriction from Claude's `system`/`init` event (it must precede any model output, list exactly `["StructuredOutput"]` as tools and no MCP servers, otherwise the child is killed and `Unsupported` returned), and validates the structured response locally against the caller's JSON Schema. The process receives `DOCLIFY_GENERATED_SESSION=1` and `DOCLIFY_BRIDGE=1`; capture hooks suppress bridge-generated events. Safe mode and no session persistence also reduce recursive capture.

`Bridge::capability` checks the installed executable's help for the required flags; `ConstrainedAuthenticationUnverified` means only that the CLI advertises them, not that authentication, model availability, or managed policy compatibility were verified; runtime tool exposure is checked per call by `execute`. The installed versions inspected were Claude Code 2.1.308 and codex-cli 0.166.0. A live run of the bridge flags against Claude Code 2.1.308 reported tools `["StructuredOutput"]`, no MCP servers and no slash commands; its init event still listed built-in plugins (`cc-plugin-*@builtin`) and agent definitions, which are unreachable without an Agent tool. The init event is the CLI's self-report: Claude's managed settings still apply even in safe mode, and users must trust the CLI and its administrator policy. Codex is deliberately unavailable and is never spawned. Evidence from codex-cli 0.166.0 local help: `codex exec --help` offers no option to disable tools, and `--sandbox` "select[s] the sandbox policy to use when executing model-generated shell commands" only. Rendering the model-visible input with `codex debug prompt-input` under an empty `CODEX_HOME` (no credentials) and `--disable shell_tool --disable unified_exec --disable code_mode_host --disable sleep_tool` still lists `functions.exec` (a JavaScript tool whose nested tools include `apply_patch`, `view_image` and MCP resource readers), `functions.request_user_input`, and `collaboration.spawn_agent`. Disabling every enabled feature does empty the rendered list, but only through `incremental_tools`: with it disabled the rendering omits the `additional_tools` item entirely (tools then travel outside the rendered input, so absence is not evidence), and with it enabled and every other feature disabled the list still contains `exec`, `wait`, `request_user_input`, `request_user_input_async` and the `collaboration` agent tools. `codex app-server` is marked experimental, so it is not a supported alternative. No objectively verifiable tool restriction exists, so the bridge fails closed; for OpenAI models, `providers::ApiProvider` is the tool-free path. `codex_visible_tools` is a diagnostic that renders the installed Codex's model-visible tools under an empty `CODEX_HOME` and working directory (no credentials, no inference) with caller-supplied flags, erroring when tools are not rendered; `execute` never uses it. Do not silently fall back to another provider.

`Bridge::execute` returns structured errors including exit status and stderr (which may contain sensitive information). Callers should retain their pending work on errors and control logging of diagnostics. A timeout kills the direct child; external CLI descendants are not guaranteed to terminate. The caller must decide what information may be sent to the selected provider, and must own all documentation writes and review state.

The bridge is a workspace member used by the CLI and pipeline. Run `cargo test -p doclify-model-bridge`. Live checks are opt-in: `DOCLIFY_LIVE_CLAUDE=1` runs one authenticated Haiku inference through `execute` using the installed `claude` and its own login in place (no credentials are copied), and `DOCLIFY_LIVE_CODEX=1` asserts the installed Codex still renders an `exec` tool, so it fails once a release removes it.

`providers::ApiProvider` supports OpenAI-compatible chat completions and Anthropic messages, plus provider model-list discovery. Set `base_url` to the provider's versioned API root and `api_key_env` to an environment variable name; the key is read only when making a request. Configured `models` are identifiers supplied by the user, not evidence of availability. Calls are synchronous and should be run on a blocking worker when integrating with Tokio. Redirects are disabled and non-loopback endpoints require HTTPS. Provider errors deliberately omit response bodies and credentials.

`providers::validate_proposals` rejects unknown fields, non-proposed review states, missing citations and unsupported kinds. It does not establish that cited identifiers exist or that a claim is true: the extraction pipeline must validate citations against its source set, retain the input and checkpoint until a validated proposal is durably stored, and require explicit review before acceptance. Neither provider calls nor validation write records, persist checkpoints, or change review state. The CLI bridge accepts a caller-provided schema; the pipeline CLI adapter applies the shared proposal schema and semantic validation. The CLI provides provider configuration and model discovery; authenticated API provider smoke tests remain absent.
