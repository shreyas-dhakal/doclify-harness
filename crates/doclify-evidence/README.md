# Doclify evidence and documentation

Read-only evidence sync and standard documentation generation (delivery phase 4).

- `sync(repo, local_dir, &SyncOptions)` reads local branches, commits (with numstat) across `--branches`, and, if `gh` is installed and authenticated, PRs with merge evidence (merged at/by, merge commit), review decision, reviews, and discussion comments (bodies capped at 1000 characters) via a single `gh pr list` call, bounded by `max_pull_requests`, `gh_timeout` (default 30s; the process is killed), and 32 MiB of output. A missing, unauthenticated, or failing `gh` is recorded as `Github::Unavailable { reason }`; local evidence still syncs. `SyncOptions { gh: None, .. }` skips GitHub. The snapshot is written to `local_dir/evidence.json`, which is rebuildable and must be in ignored local storage.
- Test evidence (`verify`): `SyncOptions::captured` takes capture hook events and queued hook/transcript jobs. A `PostToolUse` shell command matching a known test runner is an `Observed` run; its outcome comes from the exit code, `PostToolUseFailure`, or Claude's success-only `PostToolUse`, else `Unknown`. Assistant text saying tests pass is a `Claimed` run, never treated as observed. Each run records its agent, session, the HEAD it was captured at, and its scope: the exact command or the claim's sentence, nothing broader. A run is `stale` when non-documentation files changed between its revision and HEAD, or the revision is unknown. Uncommitted working-tree state is not captured by hooks, so results describe HEAD at capture only.
- Session associations (`sessions`): a commit message citing a session id is `Direct`; HEAD moving to a commit during a session is only `Suggested`.
- `file_history` and `diff` read on demand; patches are never copied into tracked docs.
- Links connect records to commits and PRs. Only evidence a record cites (`commit:<sha prefix of 7 or more characters>`, `pr:<n>`) is `Direct`; whole-token mentions of a record id in commit messages or PR title, body, or branch are `Suggested`. Nothing here changes review state, so a commit or merged PR never accepts a record.
- `docs::generate(repo, Option<&Evidence>)` writes `docs/doclify/{overview,architecture,setup,requirements,decisions,evidence,open-work}.mdx`. Accepted versions, pending proposals, and implementation state are shown separately, with record citations (`id@vN`), provenance sources and excerpts, and evidence links. Purpose, design intent, and setup steps stay explicitly `Unknown` until a reviewed record documents them; repository-observed facts are labeled as such. Abandoned experiments are listed as history, not instructions. All record text is MDX-escaped. Output is deterministic.
- Human edits are kept. The last generated copy of each page is stored in `.doclify/generated/`. When both the human and the regeneration changed a page, they are three-way merged against that copy with `git merge-file` and reported in `Report::merged`. Overlapping (or adjacent) edits are never overwritten: the new version goes to `.doclify/conflicts/<page>.mdx` and is reported in `Report::conflicts`. `docs::resolve_conflict(repo, page)` marks it reviewed by making it the new baseline. A page that existed before Doclify first generated it counts as a human edit. Commit `.doclify/generated/` and `.doclify/conflicts/` with the docs so teammates share the baseline.

Limits: merging is line-based; adjacent edits conflict. Each sync rescans up to `max_commits` (default 500) with no checkpoint. Test runners are a fixed list, and any non-doc change makes a run stale (no test-to-path mapping). Inline PR review comments are not fetched.

## CLI integration

`doclify sync` collects evidence and generates pages for the current worktree. The CLI uses worktree-local Git storage for the evidence snapshot and captured jobs.
